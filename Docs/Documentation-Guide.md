# Documentation guide

Keep durable project knowledge in Docs and dated development experience in Walkthrough. Start from İçindekiler.md and read only the topic relevant to the requested change.

Document relationships or verified methods that would otherwise require rediscovery. Describe the trigger, mechanism, conditions and observable result. Identify whether evidence comes from inspected source, a controlled fault test or a real service call. Do not present one kind as another. Technical documentation and code are English; localized product strings retain their own language.

Keep one authoritative explanation per subject and link to it. Add a new topic to the nearest index. Update the existing topic when its contract changes; do not add a competing copy. README remains the product entry point, not a second architecture reference.

Do not put transcripts, raw logs, generated test output, temporary plans or unverified fixes in Docs. Temporary tests belong in the designated NewTemp workspace. Do not turn a one-off user instruction into an invented permanent prohibition or claim user approval that was never given.

Before finishing a change, retain any new verified lesson and correct the affected topic and links. Reuse existing verification when the relevant code and conditions have not changed. Check only the links and claims affected by the documentation change.
